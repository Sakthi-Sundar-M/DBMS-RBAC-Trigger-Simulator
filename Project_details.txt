1. POSTGRESQL ROLES & ROLE-BASED ACCESS CONTROL (RBAC) PERMISSIONS
================================================================================

The system enforces strict Discretionary Access Control (DAC) using PostgreSQL 
native roles and privileges configured via GRANT and REVOKE statements. All 
authorization checks are queried dynamically at runtime from PostgreSQL's 
`information_schema.role_table_grants` and `role_column_grants`—ensuring zero 
hardcoded permission logic in the Python application layer.

--------------------------------------------------------------------------------
ROLE 1: bank_teller
--------------------------------------------------------------------------------
* Purpose & Responsibilities:
  Counter cashier responsible for processing in-branch cash deposits, opening 
  new customer accounts, and looking up customer identity records.
* Table-Level Privileges:
  - customer_accounts : INSERT, SELECT
  - customer_profiles : SELECT
  - daily_transactions: SELECT
* Column-Level Privileges:
  - customer_accounts : balance (UPDATE allowed for counter deposits/withdrawals)
* Strict Security Restrictions:
  - DENIED access to `audit_log` (cannot read or write compliance logs).
  - DENIED access to `fraud_alerts` (cannot see or log fraud cases).
  - DENIED access to `loan_applications` (cannot create or approve loans).
  - CANNOT freeze or close customer accounts (account_status is protected).

--------------------------------------------------------------------------------
ROLE 2: branch_manager
--------------------------------------------------------------------------------
* Purpose & Responsibilities:
  Executive authority responsible for branch oversight, final loan approvals, 
  account freezes, and fraud resolution.
* Table-Level Privileges:
  - customer_accounts : SELECT, INSERT
  - customer_profiles : SELECT
  - daily_transactions: SELECT
  - loan_applications : SELECT, INSERT
* Column-Level Privileges:
  - customer_accounts : account_status (UPDATE to 'FROZEN', 'ACTIVE', 'CLOSED')
  - fraud_alerts      : alert_status (UPDATE to 'RESOLVED', 'FALSE_POSITIVE')
  - loan_applications : approval_status (UPDATE to 'APPROVED', 'REJECTED')
* Strict Security Restrictions:
  - DENIED direct balance adjustments (cannot modify account balances directly).
  - CANNOT advance loans to the intermediate 'UNDERWRITE' stage (reserved for Underwriter).
  - CANNOT directly write to `audit_log` (writes occur via SECURITY DEFINER trigger).

--------------------------------------------------------------------------------
ROLE 3: fraud_analyst
--------------------------------------------------------------------------------
* Purpose & Responsibilities:
  Financial intelligence specialist investigating suspicious activity, money 
  laundering risks, and generating formal fraud reports.
* Table-Level Privileges:
  - fraud_alerts      : INSERT, SELECT
  - customer_accounts : SELECT
  - customer_profiles : SELECT
  - daily_transactions: SELECT
* Column-Level Privileges:
  - fraud_alerts      : alert_status (UPDATE to 'UNDER_INVESTIGATION')
* Strict Security Restrictions:
  - DENIED access to `loan_applications` and `audit_log`.
  - CANNOT freeze bank accounts directly (must raise alert for Branch Manager).
  - CANNOT perform financial transfers or alter balances.

--------------------------------------------------------------------------------
ROLE 4: senior_underwriter
--------------------------------------------------------------------------------
* Purpose & Responsibilities:
  Credit risk assessment officer evaluating loan files and moving qualified 
  applications into active underwriting.
* Table-Level Privileges:
  - loan_applications : SELECT
  - customer_accounts : SELECT
  - customer_profiles : SELECT
  - daily_transactions: SELECT
* Column-Level Privileges:
  - loan_applications : approval_status (UPDATE ONLY to 'UNDERWRITE')
* Strict Security Restrictions:
  - CANNOT grant final loan approval (cannot set status to 'APPROVED' or 'REJECTED').
  - CANNOT modify customer account statuses, balances, or fraud records.

--------------------------------------------------------------------------------
ROLE 5: it_security_admin
--------------------------------------------------------------------------------
* Purpose & Responsibilities:
  Information security compliance officer verifying system immutability.
* Table-Level Privileges:
  - audit_log         : SELECT (Strict read-only inspection)
* Strict Security Restrictions:
  - STRICTLY DENIED write access across all operational banking tables.
  - CANNOT view customer profiles, accounts, or transaction records directly.

--------------------------------------------------------------------------------
ROLE 6: internal_auditor
--------------------------------------------------------------------------------
* Purpose & Responsibilities:
  Independent banking supervisor conducting regulatory examinations.
* Table-Level Privileges:
  - Full read-only SELECT access across all 6 core relations:
    customer_profiles, customer_accounts, daily_transactions, fraud_alerts, 
    loan_applications, audit_log.
* Strict Security Restrictions:
  - STRICTLY DENIED all DML write privileges (INSERT, UPDATE, DELETE).

--------------------------------------------------------------------------------
AUXILIARY ROLES:
--------------------------------------------------------------------------------
* retail_customer:
  - Initiates self-service peer-to-peer transfers (`INSERT on daily_transactions`).
  - Read-only access to own account via stored procedure `secure_account_viewer`.
* csr (Customer Service Representative):
  - Read-only lookup on profiles and accounts to answer client inquiries.
* loan_officer:
  - Intake clerk registering new customer credit requests (`INSERT on loan_applications`).

2. DATABASE TABLES & COLUMN-LEVEL SCHEMA SPECIFICATIONS
================================================================================

The database is deployed on Neon Serverless PostgreSQL (PostgreSQL 16 Engine) 
utilizing SSL encrypted connections.

--------------------------------------------------------------------------------
TABLE 1: customer_profiles
--------------------------------------------------------------------------------
* Description: Master identity and Know-Your-Customer (KYC) registry.
* Columns:
  1. profile_id   : INTEGER | PRIMARY KEY | Unique customer identification number.
  2. full_name    : VARCHAR(100) | NOT NULL | Customer full legal name.
  3. phone_number : VARCHAR(20) | Customer registered contact number.
  4. kyc_status   : kyc_status_enum | ENUM('APPROVED', 'PENDING', 'REJECTED')
                    Determines eligibility for banking operations.

--------------------------------------------------------------------------------
TABLE 2: customer_accounts
--------------------------------------------------------------------------------
* Description: Active deposit and transactional checking accounts.
* Columns:
  1. account_id    : INTEGER | PRIMARY KEY | Unique account number.
  2. profile_id    : INTEGER | REFERENCES customer_profiles(profile_id) | Account owner.
  3. account_type  : VARCHAR(20) | CHECK IN ('SAVINGS', 'CURRENT', 'DEPOSITS').
  4. balance       : NUMERIC(15, 2) | NOT NULL | CHECK (balance >= 0.00)
                     Current cleared funds; negative balances strictly prohibited.
  5. account_status: account_status_enum | ENUM('ACTIVE', 'FROZEN', 'CLOSED')
                     Operational status governed by branch manager.

--------------------------------------------------------------------------------
TABLE 3: daily_transactions
--------------------------------------------------------------------------------
* Description: Double-entry financial journal recording funds transfers.
* Columns:
  1. txn_id           : SERIAL | PRIMARY KEY | Unique transaction reference.
  2. sender_id        : INTEGER | REFERENCES customer_accounts(account_id) | Source account.
  3. receiver_id      : INTEGER | REFERENCES customer_accounts(account_id) | Beneficiary account.
  4. amount           : NUMERIC(15, 2) | NOT NULL | CHECK (amount > 0.00) | Transfer amount.
  5. transaction_type : VARCHAR(20) | CHECK IN ('INTERNAL', 'ACH', 'WIRE').
  6. created_at       : TIMESTAMPTZ | DEFAULT clock_timestamp() | Execution timestamp.

--------------------------------------------------------------------------------
TABLE 4: fraud_alerts
--------------------------------------------------------------------------------
* Description: Suspicious activity reports (SAR) and AML fraud monitoring.
* Columns:
  1. alert_id     : SERIAL | PRIMARY KEY | Unique fraud incident ID.
  2. account_id   : INTEGER | REFERENCES customer_accounts(account_id) | Subject account.
  3. risk_reason  : TEXT | NOT NULL | Detailed investigation rationale.
  4. alert_status : alert_status_enum | ENUM('OPEN', 'UNDER_INVESTIGATION', 'RESOLVED', 'FALSE_POSITIVE').
  5. reported_at  : TIMESTAMPTZ | DEFAULT clock_timestamp() | Incident creation time.

--------------------------------------------------------------------------------
TABLE 5: loan_applications
--------------------------------------------------------------------------------
* Description: Credit applications tracking linear state machine progress.
* Columns:
  1. loan_id          : SERIAL | PRIMARY KEY | Unique loan file number.
  2. profile_id       : INTEGER | REFERENCES customer_profiles(profile_id) | Applicant ID.
  3. requested_amount : NUMERIC(15, 2) | NOT NULL | CHECK (requested_amount > 0.00).
  4. approval_status  : approval_status_enum | ENUM('SUBMITTED', 'UNDERWRITE', 'APPROVED', 'REJECTED')
                        Workflow state managed strictly by authorized roles.
  5. created_at       : TIMESTAMPTZ | DEFAULT clock_timestamp() | Submission date.

--------------------------------------------------------------------------------
TABLE 6: audit_log
--------------------------------------------------------------------------------
* Description: Tamper-evident, append-only compliance audit trail.
* Columns:
  1. log_id      : SERIAL | PRIMARY KEY | Sequential audit entry index.
  2. table_name  : VARCHAR(50) | Target relation mutated ('customer_accounts', 'loan_applications').
  3. record_id   : INTEGER | Primary identifier of the modified record.
  4. account_id  : INTEGER | NULLABLE | Associated bank account number if applicable.
  5. action      : VARCHAR(10) | DML operation type ('INSERT', 'UPDATE', 'DELETE').
  6. old_value   : TEXT | Snapshot of state prior to transaction.
  7. new_value   : TEXT | Committed state following transaction.
  8. changed_by  : VARCHAR(50) | PostgreSQL session user (`CURRENT_USER`).
  9. changed_at  : TIMESTAMPTZ | DEFAULT clock_timestamp() | Precise physical execution time.

3. IN-ENGINE PL/pgSQL TRIGGERS & SECURITY INVARIANTS
================================================================================

All business integrity rules, state transitions, and audit logging are enforced 
inside the PostgreSQL storage engine via 4 procedural PL/pgSQL triggers.

--------------------------------------------------------------------------------
TRIGGER 1: process_transaction
--------------------------------------------------------------------------------
* Attached Relation : daily_transactions
* Trigger Timing    : BEFORE INSERT FOR EACH ROW
* Procedural Function: process_transaction()
* Architecture & Invariants Enforced:
  1. Identity & KYC Verification:
     Both sender profile and receiver profile must have `kyc_status = 'APPROVED'`.
     If unapproved, raises:
     RAISE EXCEPTION 'KYC_CHECK_FAILED: Sender/Receiver KYC verification not approved.'
  2. Operational Health Check:
     Neither sender nor receiver account can have status 'FROZEN' or 'CLOSED'.
     If frozen, raises:
     RAISE EXCEPTION 'ACCOUNT_FROZEN_BLOCKED: Sender/Receiver account is FROZEN/CLOSED.'
  3. Fraud Investigation Guard:
     Verifies if active fraud alerts exist with status 'UNDER_INVESTIGATION' or 'FROZEN'.
     If detected, raises:
     RAISE EXCEPTION 'FRAUD_CHECK_FAILED: Account is under active fraud investigation.'
  4. Atomic Balance Settlement:
     Verifies sender available balance (`balance >= NEW.amount`).
     Deducts amount from sender and adds amount to receiver atomically:
     UPDATE customer_accounts SET balance = balance - NEW.amount WHERE account_id = NEW.sender_id;
     UPDATE customer_accounts SET balance = balance + NEW.amount WHERE account_id = NEW.receiver_id;
     If insufficient funds, raises:
     RAISE EXCEPTION 'INSUFFICIENT_FUNDS: Transfer amount exceeds available balance.'

--------------------------------------------------------------------------------
TRIGGER 2: check_loan_eligibility
--------------------------------------------------------------------------------
* Attached Relation : loan_applications
* Trigger Timing    : BEFORE INSERT FOR EACH ROW
* Procedural Function: check_loan_eligibility()
* Architecture & Invariants Enforced:
  1. KYC Prerequisite:
     Customer KYC status must be 'APPROVED'. Rejects unverified applicants.
  2. Account Health Verification:
     Rejects applicants if any linked bank accounts are 'FROZEN' or 'CLOSED'.
  3. Anti-Loan-Stacking Policy:
     Blocks applicants if they already have an existing loan in 'SUBMITTED' or 'UNDERWRITE'.
     If concurrent review exists, raises:
     RAISE EXCEPTION 'LOAN_STACKING_BLOCKED: Customer already has a loan application under review.'

--------------------------------------------------------------------------------
TRIGGER 3: enforce_loan_workflow
--------------------------------------------------------------------------------
* Attached Relation : loan_applications
* Trigger Timing    : BEFORE UPDATE FOR EACH ROW
* Security Mode     : SECURITY DEFINER (executes with elevated owner authority)
* Procedural Function: enforce_loan_workflow()
* Architecture & Invariants Enforced:
  Strict Linear State Machine: SUBMITTED -> UNDERWRITE -> APPROVED / REJECTED
  1. State 1 (SUBMITTED -> UNDERWRITE):
     Can ONLY be executed by `CURRENT_USER = 'senior_underwriter'`.
     Rejects if any other role attempts advancement.
  2. State 2 (UNDERWRITE -> APPROVED or REJECTED):
     Can ONLY be executed by `CURRENT_USER = 'branch_manager'`.
     Performs second-tier risk verification: verifies applicant account was not 
     subsequently frozen or placed under fraud alert during the underwriting cycle.
  3. Terminal State Enforcement:
     Once an application reaches 'APPROVED' or 'REJECTED', it is terminal. Any 
     further update attempt raises:
     RAISE EXCEPTION 'Workflow Error: This loan has already reached a final decision.'
  4. Stage Skipping & Backward Regression Guard:
     Blocks jumping directly from 'SUBMITTED' to 'APPROVED' (bypassing underwriting).
     Blocks moving backward from 'UNDERWRITE' back to 'SUBMITTED'.

--------------------------------------------------------------------------------
TRIGGER 4: log_audit_event
--------------------------------------------------------------------------------
* Attached Relations: customer_accounts, loan_applications
* Trigger Timing    : AFTER UPDATE FOR EACH ROW
* Security Mode     : SECURITY DEFINER
* Procedural Function: log_audit_event()
* Architecture & Invariants Enforced:
  1. Change Detection:
     Only writes to `audit_log` if status fields actually mutated 
     (`OLD.account_status IS DISTINCT FROM NEW.account_status` or 
      `OLD.approval_status IS DISTINCT FROM NEW.approval_status`).
  2. Immutable Capture:
     Inserts audit entry capturing `TG_TABLE_NAME`, record ID, `TG_OP`, old status, 
     new status, and authenticated session actor (`CURRENT_USER`).
  3. Security Privilege Separation:
     Runs as `SECURITY DEFINER` so authorized officers can update account or loan 
     records without requiring direct INSERT grants on the compliance audit table.

4. CUSTOM AI EVALUATOR MODEL ARCHITECTURE & TRAINING METHODOLOGY
================================================================================

--------------------------------------------------------------------------------
MODEL ARCHITECTURE OVERVIEW:
--------------------------------------------------------------------------------
* Model Artifact Directory: `models/dbms-trigger-evaluator`
* Base Transformer        : `sentence-transformers/all-MiniLM-L6-v2` (22.7M parameters)
* Embedding Dimensionality: 384-dimensional dense vector embeddings
* Hardware Execution      : Optimized for standard laptop CPU (Zero GPU required)
* Inference Latency       : <10 milliseconds per evaluation
* Memory Footprint        : <90 MB RAM in runtime cache

--------------------------------------------------------------------------------
SELECTIVE LAYER TRANSFER LEARNING ON CPU:
--------------------------------------------------------------------------------
Standard backpropagation across all 22.7M parameters creates ~500 MB of optimizer 
states (AdamW momentums) and activation graphs, which causes out-of-memory errors 
on standard 4GB RAM laptops. 
To achieve fast, stable, and low-memory training on CPU:
* Frozen Layers: Transformer layers 0, 1, 2, 3 and token embeddings are FROZEN.
  (18.8M frozen parameters preserving core English grammar and token positioning).
* Trainable Layers: Transformer layers 4 and 5 + Mean Pooling Head are FINE-TUNED.
  (3,696,768 trainable parameters, representing 16.3% of the network).
* Sequence Length Clamping: Set `model.max_seq_length = 96` (optimizing for 
  concise SQL clauses, transition variables, and trigger logic).

--------------------------------------------------------------------------------
CONTRASTIVE TRAINING DATASET & PAIR GENERATION:
--------------------------------------------------------------------------------
Trained on 213 domain-specific contrastive pairs derived from 48 curated competitive 
exam questions (GATE CS, ISRO Scientist, University entrances):
1. Positive Semantic Pairs (Label 0.85 - 0.95):
   - (Solution Key, In-Depth Engine Ground Truth Explanation)
   - (Exam Problem Prompt, Solution Key)
2. Subtle Invariant Hard Negative Pairs (Label 0.05 - 0.15):
   - BEFORE vs. AFTER inversion: Checks timing semantics.
   - NEW vs. OLD inversion: Checks transition variable memory buffers.
   - GRANT vs. REVOKE inversion: Checks privilege assignment direction.
   - FOR EACH ROW vs. FOR EACH STATEMENT inversion: Checks execution granularity.
   - RETURN NEW vs. RETURN NULL inversion: Checks tuple suppression semantics.
3. Cross-Topic Negatives (Label 0.05):
   - Pairs solutions from different DBMS topics to enforce distinct vector clustering.

--------------------------------------------------------------------------------
TRAINING CONVERGENCE & METRICS:
--------------------------------------------------------------------------------
* Loss Function : CosineSimilarityLoss
* Optimizer     : AdamW (lr=3e-5, zero_grad with set_to_none=True)
* Batch Size    : 4
* Epoch 1 Loss  : 0.2599
* Epoch 2 Loss  : 0.2247
* Verification  : Verified model solution achieves 100.0% cosine similarity; 
  flawed/inverted submissions are sharply discriminated down to 71% or below.

THE 31 RELATIONAL CONCEPT ARCHETYPES:
--------------------------------------------------------------------------------
The engine dynamically maps 31 distinct DBMS architectural concepts:
1.  eca                  : Event-Condition-Action model primitives and gatekeeper.
2.  insert_transition    : NEW candidate buffer vs. invalid OLD in INSERT.
3.  delete_transition    : OLD departing record archiving in DELETE.
4.  grant_revoke         : DAC least-privilege role configuration.
5.  before_after         : In-flight sanitization vs. committed serial logging.
6.  granularity          : FOR EACH ROW vs. FOR EACH STATEMENT on zero-row DML.
7.  truncate             : Why row triggers bypass TRUNCATE; statement intercept.
8.  dac_mac              : Discretionary vs. Mandatory Access Control labels.
9.  return_null          : Silent tuple suppression vs. transaction abort.
10. grant_option         : WITH GRANT OPTION delegation and CASCADE revokes.
11. column_level         : Attribute-level permissions vs. view encapsulation.
12. drop_trigger         : CASCADE vs. RESTRICT and preservation of function.
13. tg_op                : Multi-event introspection dispatching in single trigger.
14. cascading            : ACID transaction atomicity across cascading trigger chains.
15. value_guard          : Monotonic integrity guards on proposed updates.
16. security_definer     : Search_path hardening against privilege escalation.
17. when_clause          : Engine-level conditional filtering before context switch.
18. transition_tables    : REFERENCING NEW TABLE AS for set-based statement checks.
19. execution_order      : Alphabetical trigger execution sequencing.
20. set_role             : SET ROLE session context vs. session_user identity.
21. cross_relation       : Cross-table foreign aggregate synchronization.
22. timestamp            : clock_timestamp() wall-clock precision vs. NOW().
23. maker_checker        : Segregation of Duties (SoD) dual-control approvals.
24. mutating_table       : pg_trigger_depth() infinite recursion guard.
25. state_machine        : Linear lifecycle transition validation.
26. instead_of           : Updatable view routing over joined base tables.
27. append_only          : Unconditional rejection of UPDATE/DELETE on audit log.
28. deferred             : CONSTRAINT TRIGGER DEFERRABLE INITIALLY DEFERRED.
29. multi_tenant         : Session-based tenant context isolation.
30. ddl_event            : PostgreSQL Event Triggers intercepting DDL drops.
31. savepoint            : BEGIN ... EXCEPTION subtransaction error recovery.

STREAMLINED, NON-SPOONFEEDING EXAM PROMPTS:

To maintain competitive exam authenticity, problem prompts avoid spoon-feeding 
step-by-step instructions. Instead, they present concise, realistic 2–3 sentence

  "In `Passenger Airline Seat Reservation & Overbooking Control` (Commercial 
   Aviation & Flight Operations) with relations `flights` and `seat_bookings`, 
   explain how the Event-Condition-Action (ECA) rule model applies to automated 
   `booked_seats` governance. Formulate the active rule components for 
   `seat_bookings` and state which primitive acts as the execution gatekeeper."

--------------------------------------------------------------------------------
1. Interactive Buffer:
   Each problem scenario provides an independent SQL/PLpgSQL code editor

   Runs in <10ms with zero external dependencies. Validates:
   - Interaction with scenario tables (e.g. `flights`, `seat_bookings`).
   - Use of required transition variables (`NEW`, `OLD`) and timings.
   - Implementation of key invariants (e.g. `RAISE EXCEPTION`, `RETURN NEW`).
   - Returns a visual score badge, verified checks (`✓`), and missing checks (`✕`).

   Students can expand "Official Model Solution & Self-Check Rubric" anytime to 
   view the complete, production-grade PL/pgSQL function and trigger DDL along with
