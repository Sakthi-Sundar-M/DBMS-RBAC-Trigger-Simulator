1.1 Purpose & Educational Objective
-----------------------------------
This section bridges the gap between simulated UI operations and actual database
kernel code. Whenever a user selects a banking operation (or switches active
roles), this section dynamically displays the exact PL/pgSQL procedural trigger
function compiled inside PostgreSQL that guards or executes that specific action.

It proves that business logic, security constraints, and state transitions are
not running in Python or frontend application code, but are compiled in PostgreSQL's
system catalog (pg_proc, pg_trigger).

1.2 Visual Attributes & What Each Does
--------------------------------------
1. Active Operation Selector (`inspect_job`):
   - WHAT IT DOES: A dropdown menu populated with all 13 banking operations across
     the 6 core roles.
   - DEFAULT BEHAVIOR: Automatically defaults to the operation currently selected
     in the Banking Operations Simulator (Tab 1), but can be freely switched by the
     user to inspect any operation.

2. Synchronization Badge (`sync_badge`):
   - "🔄 Synced with Simulator": Appears when the inspected operation matches the
     live Simulator selection. Indicates that inputs in Tab 1 directly map to this
     trigger.
   - "Free Inspection": Appears when the user chooses to inspect a different
     operation without changing the active simulator state.

3. Role Authorization Status Badge (`role_badge`):
   - "✔️ Authorized": Indicates that the currently active role holds the required
     PostgreSQL table/column grant to execute this operation.
   - "❌ RBAC Denied": Indicates that PostgreSQL's information_schema catalog
     blocks this role from dispatching this operation (Tier-1 Access Control).

4. Visual Summary Card:
   - `trigger_title`: Displays the exact name of the PL/pgSQL trigger function
     (e.g., `process_transaction()`, `check_loan_eligibility()`).
   - `trigger_timing`: Displays the execution point and target relation:
     * BEFORE INSERT ON daily_transactions (FOR EACH ROW)
     * BEFORE INSERT ON loan_applications (FOR EACH ROW)
     * BEFORE UPDATE ON loan_applications (FOR EACH ROW, SECURITY DEFINER)
     * AFTER UPDATE ON customer_accounts (FOR EACH ROW, SECURITY DEFINER)
   - `trigger_summary`: Natural-language summary describing the exact security
     checks, solvency calculations, or state machine transitions enforced.

5. Role Context Banner (`role_hint`):
   - WHAT IT DOES: Explains the exact relationship between the active database role
     (e.g., retail_customer, branch_manager, senior_underwriter) and the inspected
     trigger.
   - EXAMPLE: For a Senior Underwriter inspecting `enforce_loan_workflow()`, it
     explains that the underwriter has authority to transition a loan from SUBMITTED
     to UNDERWRITE, but is blocked by the trigger from final APPROVAL.

6. Database Rejection Firewalls Cards:
   - Displays modular cards for each business rule enforced by the trigger.
   - Each card contains 3 attributes:
     * Firewall Name (`flabel`): The business defense rule (e.g., "Account Freeze Hold").
     * Exception Code (`ecode`): The exact error string raised by PostgreSQL
       (e.g., `ACCOUNT_FROZEN_BLOCKED`).
     * Rationale (`edesc`): Why PostgreSQL halts execution and how it triggers
       an automatic ACID Rollback.

7. Collapsible PL/pgSQL Kernel Source Drawer:
   - Expander containing the complete, syntax-highlighted PostgreSQL PL/pgSQL
     source code. Shows DECLARE blocks, variable bindings, SELECT INTO queries,
     conditional checks, RAISE EXCEPTION calls, and RETURN NEW / RETURN NULL.

8. Direct Engine Query Fallback (When No Trigger Exists):
   - Displayed for read-only queries (`SELECT`) and basic schema DML.
   - Explains the architectural reason: In ANSI SQL relational database standards,
     procedural triggers execute exclusively on row modification events (INSERT,
     UPDATE, DELETE). Read queries are handled by PostgreSQL's cost-based query
     optimizer without procedural trigger interpreter overhead.

1.4 The 4 Database Rejection Firewalls & Error Codes
----------------------------------------------------
A. `process_transaction()` Firewalls:
   1. KYC_CHECK_FAILED: Sender or receiver profile kyc_status != 'APPROVED'.
   2. ACCOUNT_FROZEN_BLOCKED: Sender or receiver account_status IN ('FROZEN', 'CLOSED').
   3. FRAUD_CHECK_FAILED: Account has an active investigation ticket in fraud_alerts.
   4. INSUFFICIENT_FUNDS: Sender ledger balance < transfer amount.

B. `check_loan_eligibility()` Firewalls:
   1. LOAN_KYC_FAILED: Applicant kyc_status != 'APPROVED'.
   2. LOAN_STACKING_BLOCKED: Applicant already has an active loan under review.
   3. LOAN_ACCOUNT_COMPROMISED: Applicant holds a FROZEN or CLOSED account.

C. `enforce_loan_workflow()` Firewalls:
   1. WORKFLOW_STAGE_SKIPPED: Prohibits jumping from SUBMITTED directly to APPROVED.
   2. WORKFLOW_BACKWARD_TRANSITION: Prohibits reverting a loan backwards.
   3. WORKFLOW_UNAUTHORIZED_ACTOR: Enforces that only Senior Underwriters move to
      UNDERWRITE and only Branch Managers issue final APPROVAL.
   4. WORKFLOW_TERMINAL_STATE: Prohibits mutating loans in APPROVED or REJECTED state.

D. `log_audit_event()` Firewalls:
   1. AUDIT_APPEND_ONLY: audit_log table permits INSERT only; UPDATE and DELETE
      privileges are strictly revoked from all users.

2.1 Purpose & Formal DBMS Theory (ECA Model)
--------------------------------------------
This section teaches formal Database Management Systems (DBMS) theory. In active
database systems, triggers are formally structured into the Event-Condition-Action
(ECA) model:
  - EVENT: What database operation invoked execution?
  - CONDITION: What predicates are evaluated against transient memory buffers?
  - ACTION: What atomic side-effects or state modifications take place?

Additionally, this section features an in-depth "Transition Variables Memory Buffer
Inspector" that dissects PostgreSQL's volatile RAM buffers (`NEW` vs `OLD`).

2.2 Primitive 1: The Event (Attributes & Behaviors)
---------------------------------------------------
- `event_timing`:
  * `BEFORE`: Fires prior to data mutation; used to validate constraints, sanitize
    inputs, or block unauthorized writes before they touch disk heap pages.
  * `AFTER`: Fires after row modification succeeds; used to cascade secondary
    operations like audit logging without locking the primary table.
  * `PRE-PARSING CHECK`: Trigger dispatch aborted at catalog level (RBAC rejection).
  * `ON DISPATCH`: Direct query engine execution for read-only queries.
- `event_type`: The SQL DML command invoking the rule (`INSERT`, `UPDATE`, `DELETE`,
  `SELECT`, or `DISPATCH ABORTED`).
- `target_table`: The target relational table registered in PostgreSQL
  (e.g., `daily_transactions`, `loan_applications`, `customer_accounts`).
- `granularity`: In PostgreSQL, triggers are declared `FOR EACH ROW` (firing
  once for each affected record) or `FOR EACH STATEMENT`. All financial triggers
  in this project operate at row granularity.
- `sec_mode`:
  * `SECURITY INVOKER`: Trigger executes with the database privileges of the user
    who issued the query.
  * `SECURITY DEFINER`: Trigger temporarily elevates privileges to execute as
    the schema owner (postgres). Crucial for `log_audit_event()`, allowing
    unprivileged users (like tellers) to append audit records without having
    direct table write access.
- `timing_desc`: Deep explanation of PostgreSQL kernel execution lifecycle.

2.3 Primitive 2: Conditions (Attributes & Behaviors)
----------------------------------------------------
- `cond_title`: Name of the validation ruleset evaluated in memory
  (e.g., "4-Tier Financial Firewall", "Linear Workflow State Machine").
- `conditions` (List of Predicates): The actual boolean logic evaluated by the
  PostgreSQL PL/pgSQL interpreter using in-memory transition variables:
  * Example: `sender.balance >= NEW.amount`
  * Example: `account_status NOT IN ('FROZEN', 'CLOSED')`
  * Example: `OLD.balance != NEW.balance OR OLD.status != NEW.status`
- `cond_status_badge`:
  * `✓ VERIFIED`: All condition predicates evaluated to TRUE; execution proceeds.
  * `✕ VIOLATED`: At least one predicate failed; trigger halts execution.
  * `❌ DENIED`: Tier-1 RBAC authorization halted execution before conditions ran.
  * `AWAITING`: Waiting for user to dispatch a simulation in Tab 1.

2.4 Primitive 3: The Action (Attributes & Behaviors)
---------------------------------------------------
- `action_badge`: Visual indicator of the database outcome:
  * `✓ TRANSACTION COMMITTED`: Successful execution committed to WAL and disk heap.
  * `✕ TRANSACTION ABORTED`: `RAISE EXCEPTION` called; automatic rollback issued.
  * `❌ ACCESS DENIED (403)`: PostgreSQL catalog halted execution.
  * `PENDING DISPATCH`: Ready for execution.
- `action_desc`: Kernel-level explanation of database state mutations, balance
  debit/credit arithmetic, or rollback behavior.
- ACID Atomicity Guarantee: Emphasizes that PostgreSQL guarantees "all-or-nothing"
  atomicity. If a trigger condition fails at step 4, steps 1-3 are rolled back
  completely with zero partial writes.

2.5 In-Memory Buffer Inspector (Transition Variables: NEW vs OLD)
-----------------------------------------------------------------
In PostgreSQL PL/pgSQL, row triggers receive two special pseudo-record variables
in transient memory:
  - `NEW`: Record holding the proposed row data (valid during INSERT and UPDATE).
  - `OLD`: Record holding the original row state on disk (valid during UPDATE and DELETE).

The Buffer Inspector dynamically alters its rendering based on 3 distinct scenarios:

SCENARIO A: Authorized DML Mutation (INSERT / UPDATE)
- Real-time simulation inputs are bound directly into the table.
- INSERT Operation:
  * `Attribute`: Schema column name (`sender_id`, `receiver_id`, `amount`, etc.).
  * `OLD Buffer (Pre-Mutation)`: Displays `NULL (Does not exist yet)`. In ANSI SQL,
    new records do not have a pre-existing state on disk.
  * `NEW Buffer (Candidate Row)`: Displays real-time inputs from Tab 1 (e.g., sender: 101,
    receiver: 102, amount: $500.00).
  * `Role`: Explains the business significance of each field.
- UPDATE Operation:
  * Displays disk values in `OLD Buffer` and proposed transitions in `NEW Buffer`.
  * E.g., `approval_status`: OLD = `SUBMITTED` -> NEW = `UNDERWRITE`.

SCENARIO B: Disallowed RBAC Request (403 Insufficient Privilege)
- What Happens in the Database:
  * PostgreSQL evaluates role privileges at Tier 1 (Parser & System Catalog stage)
    before parsing query execution trees or allocating memory buffers.
  * When a role lacks permissions (e.g., Retail Customer trying to view Audit Logs),
    PostgreSQL halts execution immediately with error 42501 (insufficient_privilege).
- What the Buffer Inspector Shows:
  * `OLD Buffer`: `NULL (Read access blocked — Disk page not loaded into RAM)`.
  * `NEW Buffer`: `NULL (Memory allocation aborted before backend slot creation)`.
  * `Procedural Trigger Engine`: `BYPASSED (Short-circuited at catalog level)`.
  * `WAL / Disk I/O`: `0 bytes written (Zero side effects)`.
- Key Educational Takeaway: Proves that PostgreSQL protects RAM and disk resources
  by failing fast at Tier 1 without unnecessarily executing triggers or loading data.

SCENARIO C: Read-Only Queries (SELECT Shared Buffer Pool)
- What Happens in the Database:
  * In relational database architecture, transition variables (`NEW` and `OLD`)
    exist solely during row-mutating operations (INSERT, UPDATE, DELETE).
  * SELECT queries bypass transition buffers entirely. PostgreSQL's executor
    allocates a `TupleTableSlot` in backend memory, reads pages from the
    PostgreSQL Shared Buffer Pool (disk cache) under an `AccessShareLock`, and
    streams rows directly to the client cursor.
- What the Buffer Inspector Shows:
  * A table mapping schema columns, PostgreSQL data types (BIGINT, TIMESTAMPTZ, NUMERIC),
    buffer path (`Shared Buffer Pool -> Client Cursor`), and mutation mode
    (`Read-Only (OLD/NEW: NULL)`).

3. QUICK VIVA VOCE REFERENCE (FREQUENT PROFESSOR QUESTIONS)
================================================================================

Q1: Why does the Buffer Inspector show NULL for both NEW and OLD when an operation
    is denied by RBAC?
A1: PostgreSQL enforces a multi-tier defense architecture. Tier 1 is the RBAC
    system catalog (`pg_class`, `pg_authid`). When an unprivileged role issues a
    query, PostgreSQL rejects it at the parse/bind stage with SQL state 42501
    (insufficient_privilege). Because authorization fails before query execution,
    the database engine never allocates memory slots for `NEW` or `OLD` records,
    saving RAM and CPU cycles.

Q2: Why doesn't the SELECT operation have an attached PL/pgSQL trigger?
A2: In relational database management systems (ANSI SQL standard), triggers are
    event-driven rules designed strictly for row-modifying events: `INSERT`,
    `UPDATE`, and `DELETE`. Read queries (`SELECT`) do not modify state and are
    optimized for throughput. Access control on `SELECT` is handled at Tier 1 via
    `GRANT SELECT` or row-level security (RLS), avoiding the overhead of trigger
    interpretation.

Q3: What is the purpose of declaring `log_audit_event()` with `SECURITY DEFINER`?
A3: By default, PostgreSQL functions run as `SECURITY INVOKER`, inheriting the
    caller's permissions. Since normal banking roles (e.g., Tellers, Customers)
    have no permission to write to the protected `audit_log` table, a normal
    trigger would fail. `SECURITY DEFINER` temporarily elevates the trigger's
    privilege to that of the function owner (`postgres`), allowing it to silently
    append forensic logs without exposing write permissions to users.

Q4: If `process_transaction()` successfully verifies KYC and account freeze status
    but fails at the solvency check, do the earlier checks remain saved?
A4: No. PostgreSQL executes the entire operation inside an atomic transaction.
    When the solvency check fails, the trigger executes `RAISE EXCEPTION`, which
    triggers an immediate `ROLLBACK`. All changes staged in volatile memory are
    discarded. Zero rows are committed to the disk heap or WAL, guaranteeing
    the ACID property of Atomicity.
