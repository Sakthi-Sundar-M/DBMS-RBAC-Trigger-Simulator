1. OVERALL PROJECT DESCRIPTION & OBJECTIVES
================================================================================
1.1 Executive Summary
The "Database Users & Roles Simulator and Trigger Visualizer" is a specialized,
high-security core banking simulation that shifts access control, financial
business rules, and workflow state machines directly into the PostgreSQL database
engine. 

Unlike traditional web applications where security checks and business rules are
written in Python, Node.js, or Java, this project adheres to a strict "Defense-in-
Depth" model where:
  - Security constraints and column-level privileges are enforced at the database
    kernel level via native PostgreSQL Role-Based Access Control (RBAC).
  - Financial checks (KYC verification, account freeze checks, fraud screening,
    balance sufficiency) and workflow state transitions are enforced inside the
    database engine using procedural PL/pgSQL triggers.
  - The Streamlit web interface contains zero hardcoded permission logic. It
    acts as a dynamic reflection of PostgreSQL's internal data dictionary
    (information_schema).
  - An interactive "Live Trace & Trigger Pipeline" and "Before/After Data State
    Diff Viewer" demystify PostgreSQL's invisible background execution,
    providing complete real-time observability into every trigger validation,
    balance delta, and transaction rollback.

1.2 Project Objectives
  1. Core Banking Simulation: Model a realistic core banking environment with
     customers, accounts, daily transactions, fraud monitoring, loan applications,
     and an immutable audit trail.
  2. Native RBAC Enforcement: Implement 6 operational and administrative roles
     using native PostgreSQL GRANT statements with surgical table- and column-
     level restrictions.
  3. Catalog-Driven UI: Dynamically query information_schema to reflect allowed
     versus blocked operations per role without hardcoded frontend if-else logic.
  4. Autonomous In-Engine Triggers: Implement 4 PL/pgSQL triggers functioning as
     firewalls, eligibility checkers, state machines, and silent audit recorders.
  5. Trigger Observability: Transform PostgreSQL's invisible trigger operations
     into an intuitive, step-by-step visual workflow (Live Trace) and snapshot
     diff viewer.
  6. Verified Robustness: Validate all trigger operations with a 12-scenario
     automated test harness covering all passing and rejection edge cases.

2. CORE NOVELTIES & INNOVATIONS
================================================================================
When asked by examiners: "What is the novelty in your project? How does it differ
from a standard web application?", present these four concrete technical pillars:

2.1 Zero-Hardcode UI via Dynamic System Catalog Reflection
  - Conventional Approach: Web developers hardcode permissions in application
    code: `if user.role == 'Bank Teller': allow_button()`. This introduces logic
    duplication, divergence between application and database permissions, and
    severe vulnerabilities if an endpoint or database port is accessed directly.
  - Novelty in This Project: The application layer contains zero permission logic.
    Instead, Streamlit dynamically queries PostgreSQL's system catalogs:
      * information_schema.role_table_grants
      * has_table_privilege(role, table, privilege)
      * has_column_privilege(role, table, column, privilege)
    If a database administrator (DBA) issues a GRANT or REVOKE command in SQL,
    the Streamlit UI updates instantly without altering a single line of Python
    code.

2.2 Demystifying the "Black Box": Real-Time Trigger Live Trace Visualizer
  - Conventional Approach: Triggers are notorious for being an invisible backend
    "black box". When an action fails, users and developers typically receive an
    opaque, uninformative database crash or generic error.
  - Novelty in This Project: The invisible execution is surfaced as an interactive
    "◈ Live Trace Pipeline". PL/pgSQL triggers raise standardized, deterministic
    exceptions (e.g., KYC_CHECK_FAILED, ACCOUNT_FROZEN_BLOCKED, FRAUD_CHECK_FAILED).
    The application parses these in-flight signals and translates them into an
    interactive checklist with green checkmarks (✓ passed), ruby crosses
    (✕ failed), and slate boxes (■ blocked), complete with downward workflow
    connector arrows (↓).

2.3 In-Engine Workflow State Machine via SECURITY DEFINER
  - Conventional Approach: Business state machines (such as loan approval
    workflows: SUBMITTED -> UNDERWRITE -> APPROVED) are almost always managed in
    application code, making them vulnerable to race conditions (TOCTOU: Time of
    Check to Time of Use) and direct SQL tampering.
  - Novelty in This Project: The state machine is physically compiled into a
    PL/pgSQL trigger (`enforce_loan_workflow`) executing with SECURITY DEFINER
    privileges. The database engine itself verifies role transitions, physically
    blocking stage-skipping, backward reversions, or unauthorized role updates
    even if the user attempts the operation via raw SQL.

2.4 Atomic Multi-Row State Diff Viewer
  - Conventional Approach: Web apps show a generic "Transaction Committed" toast
    notification without visualizing underlying table mutations.
  - Novelty in This Project: The Diff Viewer captures exact pre-transaction and
    post-commit row snapshots, visually demonstrating PostgreSQL's ACID
    Atomicity guarantee (simultaneous debit from sender and credit to receiver)
    and proving that an aborted transaction rolls back 100% of affected rows with
    zero partial writes.

4. CONNECTION OF UI WITH EXTERNALS (DATA FLOW & COMMUNICATION)
================================================================================
4.1 Secure Transport & Cloud Connection
  - The Streamlit frontend connects to Neon Serverless PostgreSQL over an
    SSL-encrypted TCP connection (Port 5432) using `psycopg2`.
  - Credentials (`DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASS`) are stored in
    `.streamlit/secrets.toml` (locally) and injected as encrypted environment
    variables on Streamlit Community Cloud. They are excluded from version
    control via `.gitignore`.
  - Neon Serverless automatically suspends compute during inactivity to conserve
    resources. To handle serverless wake-up latency and prevent connection drops,
    `db_connection.py` implements a self-healing ping check (`SELECT 1;`) before
    every query dispatch, automatically clearing stale handles and reconnecting
    if an SSL idle timeout occurs.

4.2 Role Context Switching (`SET ROLE`)
  - When the user selects a role in the Streamlit sidebar (e.g., `fraud_analyst`),
    the client dispatches:
        `SET ROLE fraud_analyst;`
        `SET TIME ZONE 'Asia/Kolkata';`
  - All subsequent statements inside that transaction are evaluated directly by
    PostgreSQL under that role's security context.
  - After execution, the connection executes `RESET ROLE;` to return the session
    cleanly to the default pooler state.

4.3 Catalog Introspection Protocol (Dynamic Permission Reflection)
  - Before rendering any job button, `check_table_permission()` queries:
        `SELECT has_table_privilege(%s, %s, %s);`
    or for column-specific actions (e.g. Branch Manager updating status):
        `SELECT has_column_privilege(%s, %s, %s, %s);`
  - If PostgreSQL returns `False`, the UI prepends `❌` to the job name and
    immediately displays an "Access Denied by RBAC" banner if selected.
  - If PostgreSQL returns `True`, the UI prepends `✔️` and dynamically generates
    the appropriate parameter form inputs (text inputs, number fields, dropdowns).

4.4 Exception Handling & Signal Propagation to Live Trace
  - When a user submits an operation, `execute_action_with_snapshot()`:
    1. Pre-Query Snapshot: Queries target rows (e.g., sender and receiver
       account balances) and saves their state in memory.
    2. Execution: Dispatches the user's SQL statement inside the active role.
    3. Trigger Interception: If a business rule fails, the PL/pgSQL trigger raises
       a descriptive exception with a deterministic prefix:
         `RAISE EXCEPTION 'KYC_CHECK_FAILED: Customer KYC is PENDING.';`
    4. Exception Capture: `db_connection.py` intercepts `psycopg2.Error`. Because
       an unhandled exception was raised, PostgreSQL automatically issues a
       complete `ROLLBACK` to the start of the transaction.
    5. UI Parsing: `parse_trigger_error()` extracts the error code (`KYC_CHECK_FAILED`)
       and cleans the message for presentation.
    6. Live Trace Rendering: `visualizer.py` matches the code to the pipeline:
         Step 1 (KYC): Failed (✕)
         Step 2 (Account Status): Blocked (■)
         Step 3 (Fraud Check): Blocked (■)
         Step 4 (Transfer Execution): Blocked (■)
    7. Diff Viewer: Captures post-query state, detects zero changes, and displays
       the `[TRANSACTION ABORTED]` card confirming atomic rollback.

5. RATIONALE: WHY THIS SPECIFIC ARCHITECTURAL SPLIT-UP IS USED
================================================================================
When examiners ask: *"Why did you design the system with this specific split-up
between the frontend, database catalogs, and PL/pgSQL triggers?"*, provide these
core architectural rationales:

5.1 Elimination of TOCTOU (Time of Check to Time of Use) Race Conditions
  - In web-tier security, a program checks if account balance > 1000 at time T1,
    and issues an update at time T2. In a concurrent banking system, another
    thread could withdraw the funds between T1 and T2.
  - In our architecture, the `BEFORE INSERT` trigger (`process_transaction`)
    locks the row and performs validation inside the exact same database
    transaction as the mutation. Race conditions are mathematically eliminated.

5.2 Defense-in-Depth & Client Agnosticism
  - If security logic resides in Python/Streamlit, anyone accessing the database
    through a different client (e.g. pgAdmin, command-line `psql`, or a mobile
    API) completely bypasses the security rules.
  - By placing RBAC in PostgreSQL system catalogs and business rules in PL/pgSQL
    triggers, the database defends itself. No client—regardless of technology—
    can bypass the rules.

5.3 Performance Optimization via Set-Based Processing
  - Trigger logic runs directly inside PostgreSQL's memory space on the server.
  - Instead of making multiple round-trip network hops across the internet
    (Frontend -> Backend -> Database -> Backend -> Frontend) to check KYC, check
    fraud, check balance, and then update, a single SQL command triggers all
    checks locally within milliseconds.

5.4 Separation of Concerns
  - Presentation Layer (Streamlit): Exclusively responsible for rendering, user
    interaction, visual telemetry, and snapshot differentials.
  - Introspection Layer (`db_connection.py`): Mediates communication and maps
    database signals to UI components.
  - Kernel Layer (PostgreSQL): Solely responsible for data storage, privilege
    validation, constraint enforcement, and audit preservation.

6. DATABASE DESIGN, ROLES & PL/PGSQL TRIGGER SPECIFICATIONS
================================================================================
6.1 Core Tables on Neon PostgreSQL
  1. `customer_profiles`: profile_id (PK), full_name, kyc_status (APPROVED,
     PENDING, REJECTED), phone_number, created_at.
  2. `customer_accounts`: account_id (PK), profile_id (FK), balance,
     account_status (ACTIVE, FROZEN, CLOSED), account_type.
  3. `daily_transactions`: transaction_id (PK), sender_id (FK), receiver_id (FK),
     amount, transaction_type, transaction_date.
  4. `fraud_alerts`: alert_id (PK), account_id (FK), risk_reason, alert_status
     (OPEN, UNDER_INVESTIGATION, FALSE_POSITIVE, RESOLVED), flagged_at.
  5. `loan_applications`: loan_id (PK), profile_id (FK), requested_amount,
     approval_status (SUBMITTED, UNDERWRITE, APPROVED, REJECTED), created_at.
  6. `audit_log`: log_id (PK), table_name, record_id, account_id, action,
     old_value, new_value, changed_by, changed_at.

6.2 Six PostgreSQL Roles & Privilege Matrix
  1. `bank_teller`: Basic operations. INSERT on daily_transactions, UPDATE on
     customer_accounts.balance (deposits/withdrawals). Blocked from changing
     account_status, loan approval_status, or viewing audit logs.
  2. `branch_manager`: Administrative authority. Surgical column UPDATE on
     customer_accounts.account_status (freeze/unfreeze), fraud_alerts.alert_status,
     and final loan approvals. Blocked from directly modifying account balances.
  3. `fraud_analyst`: Risk intelligence. INSERT and SELECT on fraud_alerts.
     Strictly blocked from modifying customer accounts or account balances.
  4. `senior_underwriter`: Loan vetting. Granular UPDATE on loan_applications
     restricted solely to transitioning applications from SUBMITTED to UNDERWRITE.
  5. `it_security_admin`: System monitoring. Exclusive SELECT access to the
     immutable audit_log table. Blocked from all operational financial tables.
  6. `internal_auditor`: Regulatory oversight. Broad, read-only SELECT across
     all core tables to verify financial compliance. Zero write/update access.

6.3 Four Deployed PL/pgSQL Triggers
  1. `process_transaction` (BEFORE INSERT on daily_transactions):
     - Pipeline: Verifies sender/receiver existence -> Checks KYC approval ->
       Rejects frozen/closed accounts -> Blocks if active fraud alert exists ->
       Verifies balance sufficiency -> Atomically debits sender and credits
       receiver.
  2. `check_loan_eligibility` (BEFORE INSERT on loan_applications):
     - Pipeline: Checks applicant KYC approval -> Verifies applicant holds no
       frozen accounts -> Verifies no fraud alerts on file -> Enforces anti-loan
       stacking (blocks new loan if existing loan is in SUBMITTED/UNDERWRITE).
  3. `enforce_loan_workflow` (BEFORE UPDATE on loan_applications):
     - Pipeline: Enforces linear state machine: SUBMITTED -> UNDERWRITE -> APPROVED.
       Blocks stage skips (e.g. SUBMITTED directly to APPROVED). Blocks backward
       transitions (e.g. UNDERWRITE back to SUBMITTED). Uses SECURITY DEFINER to
       enforce role separation.
  4. `log_audit_event` (AFTER UPDATE on customer_accounts & loan_applications):
     - Pipeline: Executes silently via SECURITY DEFINER. Resolves actor role,
       table name, record ID, account ID, old values, new values, and timestamp,
       inserting a permanent record into `audit_log`.

8. PROFESSOR & EXAMINER VIVA VOCE DEFENSE GUIDE (QUESTIONS & ANSWERS)
================================================================================
Review 1 at VIT Chennai typically focuses on core database concepts, architecture,
and schema validation. Be prepared with these exact answers:

Q1: "Why enforce access control in PostgreSQL instead of writing `if/else` checks
     in Python or Streamlit?"
A1: "Because application-level checks violate the Principle of Least Privilege
     and are vulnerable to TOCTOU race conditions. If an attacker accesses the
     API or database directly, application-layer checks are completely bypassed.
     By enforcing RBAC at the PostgreSQL kernel level using SQL GRANT statements,
     the database is the ultimate single source of truth, guaranteeing security
     regardless of which client connects."

Q2: "How does your Streamlit application know which actions to allow or deny
     without hardcoding role permissions in Python?"
A2: "The application uses Dynamic Metadata Reflection. It queries PostgreSQL's
     `information_schema.role_table_grants` and system functions `has_table_privilege()`
     and `has_column_privilege()`. If a DBA grants or revokes a privilege in SQL,
     the Streamlit UI automatically renders the allowed (✔️) or denied (❌) state
     in real time without any code modification."

Q3: "What is the difference between a table-level grant and a column-level grant
     in your system?"
A3: "A table-level grant permits an action across all columns of a table. In our
     banking system, this is too coarse. For instance, a Branch Manager needs
     authority to freeze an account by updating `account_status`, but must never
     tamper with the customer's `balance`. We issue a column-level grant:
     `GRANT UPDATE (account_status) ON customer_accounts TO branch_manager;`
     If the Branch Manager attempts to update `balance`, PostgreSQL blocks the
     statement with `psycopg2.errors.InsufficientPrivilege`."

Q4: "What happens inside PostgreSQL when a transaction violates a trigger rule?"
A4: "The trigger executes `RAISE EXCEPTION`. PostgreSQL immediately terminates
     the query and triggers an automatic ROLLBACK to the transaction start.
     Because PostgreSQL enforces ACID atomicity, zero partial mutations occur.
     Our application intercepts the descriptive exception prefix and displays
     the exact blocking reason in the Live Trace UI."

Q5: "Why did you use `SECURITY DEFINER` in the loan workflow trigger?"
A5: "By default, PostgreSQL triggers execute with `SECURITY INVOKER` (the privileges
     of the current user). However, when a Senior Underwriter transitions a loan
     from `SUBMITTED` to `UNDERWRITE`, the system must update audit logs and
     verify system state that the underwriter does not own. `SECURITY DEFINER`
     temporarily elevates the trigger execution to the function owner's privilege,
     allowing secure, encapsulated state transitions without giving the user
     excessive direct table permissions."

Q6: "How did you verify the correctness of your triggers?"
A6: "We engineered an automated test harness in `tests/test_triggers.py` that
     executes 12 distinct test cases directly against our live Neon database.
     It tests valid transfers, KYC rejections, frozen account blocks, fraud
     interceptions, loan stacking blocks, workflow stage skipping, backward
     workflow reversions, and audit log generation. All 12 tests passed (100% green)."
